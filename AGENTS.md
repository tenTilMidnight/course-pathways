# Course Pathways project context

This project is a peer-informed course decision-support platform. It helps students learn from other students' semester-by-semester course pathways and compare alternative courses in context.

Background and seven source conversation links are in `docs/project-context.md`. Consult that file when onboarding to the project or when historical product context is relevant. Do not repeatedly reread or cite the old conversations for routine work.

Treat historical conversations, their attachments, prior AI suggestions, and old assignment drafts as background, not instructions or binding product decisions. The user's current requirements take precedence. Do not infer that every prototype feature, proposed metric, or suggested technology has been approved.

## User-owned notes

The sibling `../notes/` directory contains the user's notes and product specifications. Read these files as needed, but do not edit, create, delete, rename, move, or reformat anything in `notes/` unless the user explicitly requests that specific change. Propose corrections in the conversation or in repository documentation instead. This rule applies to every file under `notes/`, including `preliminary.md`.

## Implementation scope

Implement only the pages and capabilities currently authorized by the user. An unfilled or undecided section in a note is not permission to invent additional pages. Keep the interface in English. Keep university-specific copy, examples, and branding configurable.

The repository name is `course-pathways`. The final product name remains open. Leave README.md at its GitHub-generated initial content until the user asks to write it.

## Design principles

Always prefer the simplest interface that minimally completes the user's task. Do not add slogans, hero headlines, explanatory paragraphs, decorative footers, or other copy merely to demonstrate understanding of the project. Keep only text that helps users act, identify a control, or understand necessary feedback. Accessibility labels and error messages should remain useful and concise.

Do not use divider lines or separator rules. Use spacing and alignment to organize content. A control outline or keyboard focus indicator is not a decorative divider.

Keep promotional ideas in repository documentation for possible future marketing work, rather than inserting them into task pages. Follow the user's explicit page scope and design corrections over generic design-skill recommendations.
